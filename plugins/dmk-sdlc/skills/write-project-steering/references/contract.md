# Contract Branch Template — Statement of Work (SOW)

**분기**: `contract` (수탁 / 고객 발주 프로젝트)
**산출물 명칭**: *Statement of Work (SOW)*
**산출 위치**: Project DB 해당 프로젝트 페이지 본문

> **이 템플릿이 다루는 것**
>
> 발주사와의 *합의된* 약속의 SSOT — 범위, 인수 기준, 산출물, 스테이크홀더, SLA, 변경 관리 절차. 코딩 에이전트가 매 세션 시작 시 fetch하여 *무엇이 합의된 일인가*를 인식하는 기준.
>
> **이 템플릿이 다루지 않는 것**
>
> 활성 위험, 미해결 이슈, 일정 변동, 예산 초과 추적 — Initiative 레이어로.
>
> **PMI 표준과의 관계**
>
> SOW는 *계약 산출물*이고 Project Charter는 *내부 거버넌스*다. 본 템플릿은 SOW에 해당. 내부 위임·의사결정 권한 같은 거버넌스 사항이 필요하면 별도 Initiative 또는 Repo Steering으로.
>
> **이 템플릿의 예시**
>
> 본 템플릿의 모든 도메인 예시(고객사명, 산업, 산출물 명, 인수 항목 등)는 *형태를 보여주기 위한 illustrative*다. 실제 작성 시 발주사·과제의 실제 값으로 대체한다.

## 권장 작성 순서

1. **Customer Context**
2. **Project Purpose & Background**
3. **Glossary** ← 이후 모든 섹션이 사용
4. **Scope (In-Scope Deliverables)**
5. **Out of Scope**
6. **Acceptance Criteria**
7. **Deliverables Schedule (Milestones)**
8. **Stakeholders & Roles**
9. **Pricing & Payment Terms**
10. **SLA & Constraints**
11. **Change Management Process**
12. **Resolved Assumptions**

근거: Customer/Purpose가 frame → Glossary가 어휘 제공 → Scope/Out-of-Scope 쌍이 범위 정의 → Acceptance가 Scope에 의존 → Deliverables Schedule가 Acceptance에 의존 → Stakeholders가 모든 인수·승인 주체 정의 → Pricing/SLA/Change Management는 횡단 계약 조건.

---

## 1. Customer Context

**목적**: 발주사·과제의 외부 frame. *우리가 누구를 위해 일하는가*.

### 결정에 필요한 입력

- 발주사 공식 법인명 / 사업부 / 담당 부서?
- 발주사 산업 / 규모 / 사내 IT 성숙도?
- 이 과제의 *발주 사유* — 왜 외주인가, 왜 우리인가?

### 빼먹기 쉬운 결정 점검

- 계약 *주체*가 발주사 본사인가 자회사인가? (대금 청구·법적 책임 주체)
- *최종 사용자*가 발주사 내부인가 발주사의 고객인가?
- 발주사가 이미 보유한 시스템과의 관계가 명시되었는가?

---

## 2. Project Purpose & Background

**목적**: 이 프로젝트가 *무엇을 해결*하는가. 발주사 관점에서 1단락.

### 결정에 필요한 입력

- 발주사가 현재 *어떻게* 이 일을 처리하고 있는가, 무엇이 문제인가?
- 이 프로젝트 *없이는* 어떤 비즈니스 비용이 계속 발생하는가?
- 이 프로젝트의 *성공 정의*가 발주사 측에서 무엇인가? (정량/정성 모두 가능)

### 빼먹기 쉬운 결정 점검

- 성공 정의가 *우리가 통제 가능한* 항목으로 표현되었는가? (예: "매출 10% 증가"는 발주사 책임이 더 큼 → 인수 기준으로 부적절)
- *과거 시도*가 있었는가? 있었다면 왜 실패했는가?
- 이 과제가 발주사 내부 *어느 단계의 의사결정*을 거쳐 왔는가? (이사회 / 부서 / 실무)

---

## 3. Glossary

**목적**: 발주사 도메인의 ubiquitous language 정의. 문서·산출물·회의에서 동일 단어가 동일 의미로.

### 결정에 필요한 입력

- 발주사가 사내에서 쓰는 *고유 용어*는? (산업 표준어와 다를 수 있음)
- 우리 표준 어휘와 발주사 어휘가 충돌하는 항목은?
- 약어(약칭)는?

### 빼먹기 쉬운 결정 점검

- 각 정의가 *반례*를 포함하는가?
- 산출물 문서에 노출될 용어와 *내부 코드 식별자*의 매핑이 명시되었는가?
- 동음이의어는 명시적으로 분리되었는가?

### 형식 (illustrative)

| 한국어/약어 | 영어 식별자 | 정의 | 반례/주의 |
|---|---|---|---|
| {term} | {identifier} | {definition} | {what it is NOT} |

---

## 4. Scope (In-Scope Deliverables)

**목적**: *우리가 인도하기로 약속한* 산출물의 enumerated 목록. 이 목록에 없으면 인도 의무 없음.

### 결정에 필요한 입력

- 인도할 *산출물*의 종류는? (소프트웨어 모듈 / 문서 / 교육 / 운영 이양 등)
- 각 산출물의 *형태*는? (소스코드 zip / 빌드 artifact / 호스팅 서비스 / PDF 문서 등)
- 각 산출물의 *전달 채널*은? (Git 레포 / 메일 / 발주사 시스템 등)

### 빼먹기 쉬운 결정 점검

- 각 산출물에 *식별자*가 있는가? (`D-001`, `D-002` …)
- 산출물끼리 *의존성*이 명시되었는가?
- *3rd party 라이선스*가 포함되는 경우 그 라이선스 책임 주체가 정의되었는가?
- *데이터*도 산출물에 포함되는가? (이전 데이터 / 마이그레이션 결과)

### 형식 (illustrative)

| ID | 산출물 | 형태 | 전달 채널 | 의존성 |
|---|---|---|---|---|
| D-001 | {deliverable name} | {form} | {channel} | {depends on} |

---

## 5. Out of Scope

**목적**: *명시적으로 인도하지 않는 것*. 발주사 측 기대 관리와 *변경 요청 시 부과 근거*. SOW의 가장 분쟁 친화적 섹션.

### 결정에 필요한 입력

- 발주사가 *기대할 가능성이 있으나* 합의에서 빠진 것은?
- 인접한 시스템·기능이지만 *우리 책임 밖*은?
- *유지보수·운영*이 범위 외인 경우 그 명시.

### 빼먹기 쉬운 결정 점검

- 각 Out-of-Scope 항목에 *왜 빠졌는지* 1줄 근거가 있는가? (없으면 발주사가 "당연히 포함이라고 생각했다"고 주장)
- *데이터 마이그레이션*의 책임 주체가 명시되었는가?
- *기존 시스템 연동*이 빠진 경우 인터페이스 책임이 발주사인지 명시되었는가?
- *교육/운영 이양/사용자 가이드*가 빠진 경우 명시되었는가?

---

## 6. Acceptance Criteria

**목적**: 각 Scope 산출물이 *언제 인도된 것으로 인정*되는가의 객관 기준. 인수 검수의 기준.

### 결정에 필요한 입력

- 각 D-### 산출물의 *인수 조건* — 측정 가능한 형태로?
- 인수 *주체*는 누구인가? (발주사 측 누가 sign-off)
- 인수 *방법*은? (시연 / 테스트 결과 제출 / 운영 환경 동작 / 문서 검토)

### 빼먹기 쉬운 결정 점검

- 각 인수 조건이 *주관 평가가 아닌 객관 검증* 가능한가? ("UI가 직관적이다"는 인수 조건이 아니다)
- *부분 인수*가 가능한가, 전체 인수 일괄인가?
- 인수 *기한*이 산출물 인도 후 며칠인가? (기한 경과 시 자동 인수 간주 여부)
- *불합격* 시 절차는? (재인도 횟수 제한 / 책임 주체 / 비용 부담)

### 형식 (illustrative)

| 산출물 ID | 인수 조건 | 검증 방법 | 인수자 |
|---|---|---|---|
| D-001 | {measurable criterion} | {method} | {who signs off} |

---

## 7. Deliverables Schedule (Milestones)

**목적**: 인도 일정의 SSOT. 마일스톤 = (산출물 묶음 + 인수일).

> **주의**: 일정 자체는 시간 의존이지만, 계약상 *합의된 일정*은 SOW의 일부다. 일정 변경은 Section 11 Change Management Process를 거친다. 따라서 SOW에 포함하되, 변동 추적은 Initiative로 분리.

### 결정에 필요한 입력

- 마일스톤 단위는? (월별 / 분기별 / 이벤트 기반)
- 각 마일스톤에 *어느 산출물*이 묶이는가?
- 각 마일스톤의 *인수 시점*은?

### 빼먹기 쉬운 결정 점검

- *발주사 측 작업*이 선행 조건인 마일스톤이 식별되었는가? (발주사 지연 시 우리 일정에 미치는 영향)
- *공휴일/연말연시* 같은 외부 일정이 반영되었는가?
- 마일스톤 *지연 시* 패널티/인센티브가 정의되었는가?

### 형식 (illustrative)

| 마일스톤 | 산출물 | 인수일 | 발주사 측 선행 조건 |
|---|---|---|---|
| M1 | D-001, D-002 | {YYYY-MM-DD} | {prerequisite} |

## 8. Stakeholders & Roles

**목적**: 의사결정·인수·커뮤니케이션의 *주체* 명시. *이름이 아니라 역할*. (단, 명시적으로 단일 인물의 권한이 필요한 경우 이름 포함 가능)

### 결정에 필요한 입력

- 발주사 측 *PM*은 누구이며 권한 범위는?
- 발주사 측 *최종 의사결정자*는 누구인가? (PM과 다를 수 있음)
- 발주사 측 *기술 협의 카운터파트*는?
- 우리 측 *PM / 기술 리드 / 산출물 책임자*는?

### 빼먹기 쉬운 결정 점검

- 의사결정자와 PM이 분리된 경우, *이슈 escalation 경로*가 명시되었는가?
- 발주사가 *3rd party 외주사*를 추가로 고용한 경우 그 협업 경계가 명시되었는가?
- 발주사 *법무·구매팀*과의 접촉 규약은? (계약 변경 시 누구를 거치는가)

---

## 9. Pricing & Payment Terms

**목적**: 대금 청구·지급의 SSOT. 계약서에 적힌 그대로.

### 결정에 필요한 입력

- 총 계약 금액과 *세금* 처리?
- 청구 일정 — 마일스톤 연동인가, 정기인가?
- 지급 조건 — 청구 후 며칠?
- *지연 이자* 또는 *조기 지급 할인*?

### 빼먹기 쉬운 결정 점검

- 청구가 *인수 완료 후*인가, *납품 후*인가? (둘은 다르다)
- 발주사 *내부 결제 절차*의 표준 소요 기간이 반영되었는가?
- *환불/감액* 조건은?
- 통화·환율 처리(외화 계약 시)?

---

## 10. SLA & Constraints

**목적**: *운영*과 관련된 약속과 제약. 가용성, 성능, 보안, 데이터 거주성.

### 결정에 필요한 입력

- 운영 책임이 우리에게 있는가? 있다면 가용성 SLA(예: 99.5% / 99.9%)는?
- *응답 시간 SLA*가 있는가? (장애 / 문의)
- 데이터 *거주성·보존* 제약? (해외 클라우드 사용 가능 여부 등)
- 보안 컴플라이언스 요구사항? (ISMS / SOC2 / 개인정보보호 / 의료법 등)

### 빼먹기 쉬운 결정 점검

- *측정 방법*이 정의되었는가? (가용성을 어디서 측정 / 누가 보고)
- SLA 미달 시 *패널티*가 정의되었는가? (감액 / 무상 연장 / 재시도)
- 외부 의존(예: 클라우드 제공자) 장애가 SLA에 어떻게 반영되는가? (force majeure 정의)
- *근무 시간* 정의 — 24/7인가, 평일 09–18인가?

---

## 11. Change Management Process

**목적**: Scope·일정·금액의 *변경 요청* 처리 절차. SOW 분쟁 가장 흔한 원천 — 따라서 *항상 명시*.

> **출처**: SOW 메인스트림 표준에서 별도 섹션으로 권장됨 (PMBOK / Aalpha 가이드 등).

### 결정에 필요한 입력

- 변경 요청은 *누가* 제출하고 *누가* 승인하는가?
- 변경 영향 평가 *시한*은? (요청 후 며칠 내 회신)
- 변경 요청을 *문서화*하는 형식은? (CR-### 식별자 / 영향 분석 / 견적 / 양측 sign-off)
- 변경 *최소 단위*는? (시간당 / 일 단위 / 정액)

### 빼먹기 쉬운 결정 점검

- *긴급 변경*과 *통상 변경*의 절차가 분리되었는가?
- *우리 측 발견 변경*(예: 기술적 제약으로 원안 불가)의 절차도 명시되었는가? (한쪽만 명시되면 분쟁)
- 변경이 *누적되는* 경우의 처리는? (총량 제한 / 재계약 트리거)
- 변경 *거절* 권한은 양측 모두에게 있는가?

---

## 12. Resolved Assumptions

**목적**: 명시적으로 결정되어 *invariant가 된* 가정. 발주사와 합의된 것이 핵심. 미해결 가정은 여기 들어오지 않는다 (Initiative로).

### 결정에 필요한 입력

- 발주사가 *제공*하기로 한 것은? (테스트 데이터 / 운영 환경 접근 / 인터뷰 시간 등)
- 우리가 *전제*하는 발주사 측 조건은? (예: 기존 시스템 X가 안정 동작 / 인증서 기 발급)
- 외부 환경에 대한 *공유된 가정*은? (예: 정부 정책 / 환율 범위)

### 빼먹기 쉬운 결정 점검

- 각 가정에 *검증자(발주사 측 누구) / 시한*이 명시되었는가?
- 가정이 *깨질 경우*의 절차가 명시되었는가? (Section 11 Change Management로 자동 라우팅?)
- *발주사 미제공*에 대한 책임 분담이 명시되었는가? (지연 / 비용)
