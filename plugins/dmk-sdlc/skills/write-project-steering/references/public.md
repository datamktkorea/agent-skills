# Public Branch Template — RFP Response

**분기**: `public` (공공 / RFP 대응)
**산출물 명칭**: *RFP Response*
**산출 위치**: Project DB 해당 프로젝트 페이지 본문

> **이 템플릿이 다루는 것**
>
> 발주처(공공기관)의 RFP에 대한 우리의 *체계적 응답*. 요구사항 추적성(traceability), 컴플라이언스, 기술 접근, 인력, 과거 수행 실적 — 공공 조달 메인스트림 응답 구조.
>
> **이 템플릿이 다루지 않는 것**
>
> 활성 위험, 대응팀 일정 변동, 미해결 이슈 — Initiative 레이어로.
>
> **공공 조달 표준과의 관계**
>
> 본 템플릿은 *국제 메인스트림*(Technical Proposal + Price Proposal 구조)을 기반으로 한다. 한국 공공 조달의 특수성(국가계약법, 소프트웨어 진흥법, 나라장터·G2B 양식 등)은 발주처 RFP 본문이 1차 권위이며, 본 템플릿은 *내부 SSOT*로서 그 응답을 *조직된 형태로 보존*하는 것이 목적이다. 제출 양식 변환은 별도 작업.
>
> **이 템플릿의 예시**
>
> 본 템플릿의 모든 도메인 예시(기관명, 사업명, 인력 직급, 실적명 등)는 *형태를 보여주기 위한 illustrative*다. 실제 작성 시 발주처·사업의 실제 값으로 대체한다.

## 권장 작성 순서

1. **Glossary** ← RFP 어휘 먼저
2. **RFP Requirement Traceability** ← 모든 응답의 spine
3. **Compliance Matrix** ← Traceability와 1:1
4. **Regulatory & Standards Alignment**
5. **Technical Approach**
6. **Management Approach & Key Personnel**
7. **Past Performance**
8. **Deliverables Schedule**
9. **Audit & Reporting Response**
10. **Resolved Assumptions**
11. **Executive Summary** ← 마지막에 작성 (앞 섹션의 요약이므로)

근거: RFP 어휘를 먼저 정렬 → Requirement Traceability가 모든 응답의 spine → Compliance Matrix는 Traceability에 1:1 → Regulatory가 Technical Approach의 제약 → Technical Approach 다음 Management/Personnel/Past Performance(인력·실적은 기술 접근에 의존) → Deliverables/Audit는 운영 측 → Executive Summary는 모든 섹션을 요약하므로 마지막.

## 1. Glossary

**목적**: RFP 본문의 어휘와 우리 응답 어휘의 정렬. 발주처 어휘와 우리 어휘가 다를 때, *발주처 어휘*를 우선 사용.

### 결정에 필요한 입력

- RFP 본문에서 정의된 *공식 용어*는? (그대로 차용)
- RFP에 등장하지만 *정의가 모호한* 용어는? (우리가 해석을 명시)
- 우리 표준 어휘와 RFP 어휘의 *충돌* 항목은?

### 빼먹기 쉬운 결정 점검

- 약어가 *최초 등장 시 풀어쓴 형태*로 정의되었는가?
- RFP에 등장하는 *법령·표준 인용*이 정확한 조항으로 식별되었는가? (예: "정보통신망법 제28조")
- 발주처 내부 시스템·DB명이 등장한다면 그것이 우리 응답에서 *어떻게 명시되는지* 합의되었는가?

### 형식 (illustrative)

| 용어 | RFP 정의 | 우리 응답에서의 사용 | 비고 |
|---|---|---|---|
| {term} | {as defined in RFP} | {how we use it} | {note if differs} |

## 2. RFP Requirement Traceability

**목적**: RFP의 *모든 요구사항*을 추출하여 식별자(REQ-###)로 부여. 이후 모든 응답이 이 식별자를 참조한다. *공공 평가의 가장 강력한 가산점*은 traceability.

### 결정에 필요한 입력

- RFP에 명시된 *기능 요구사항* 전체?
- RFP에 명시된 *비기능 요구사항*(성능, 보안, 가용성)?
- RFP에 명시된 *프로세스 요구사항*(보고, 검수, 형상관리)?
- RFP에 명시된 *제출물 요구사항*(산출물 종류·형식)?

### 빼먹기 쉬운 결정 점검

- RFP의 *모든* 요구사항이 추출되었는가? (놓침 = 평가 감점)
- *암묵 요구사항*(법령 인용으로만 등장)이 명시화되었는가?
- 요구사항 간 *상충*이 식별되었는가? (있다면 발주처에 사전 질의)
- RFP의 *우선순위 표기*(필수/선택/권장)가 보존되었는가?

### 형식 (illustrative)

| ID | 출처 (RFP 페이지/조항) | 요구사항 | 분류 | 우선순위 |
|---|---|---|---|---|
| REQ-001 | RFP §3.1.1 | {requirement} | 기능/비기능/프로세스/제출물 | 필수/선택/권장 |

## 3. Compliance Matrix

**목적**: 각 REQ-### 에 대한 우리의 *준수 선언*과 *근거 위치*. 평가위원이 가장 먼저 보는 표. **Section 2와 1:1 매핑**.

### 결정에 필요한 입력

- 각 REQ에 대한 *준수 상태*: 완전 준수 / 부분 준수 / 대안 제시 / 미준수
- 부분 준수·대안 제시의 *근거 설명*?
- 준수의 *증빙 위치* (본 응답서의 어느 섹션·어느 산출물)?

### 빼먹기 쉬운 결정 점검

- 모든 REQ가 누락 없이 매트릭스에 들어갔는가? (자동 검증 대상 — Phase 2.4)
- *미준수* 항목이 있다면 그 사유와 대안이 충분히 설명되었는가? (단순 "미준수"는 자동 탈락 위험)
- 부분 준수의 *어느 부분*이 빠졌는지 명확한가?
- *대안 제시*의 경우, 발주처가 그 대안을 인정해야 하는 *이유*가 들어 있는가?

### 형식 (illustrative)

| REQ-ID | 준수 상태 | 근거 위치 | 비고 |
|---|---|---|---|
| REQ-001 | 완전 준수 | §5 Technical Approach 5.2 | — |
| REQ-007 | 부분 준수 | §5.4 + §10 가정 | {what's missing and why} |

## 4. Regulatory & Standards Alignment

**목적**: 적용 법령·표준·지침에 대한 우리의 준수 방안. RFP가 명시한 것 + RFP가 명시하지 않았으나 *해당 사업에 적용*되는 것.

### 결정에 필요한 입력

- RFP가 명시한 법령·표준은?
- 사업 성격상 *추가로 적용되는* 것은? (개인정보보호법, 정보통신망법, 의료법, 전자정부법, 클라우드컴퓨팅법, 정보보호 관련 고시 등)
- 적용 *국제 표준*은? (ISO27001, ISO9001, ISMS-P 등)
- 발주처가 *내부적으로* 운영하는 보안·운영 지침이 인용되어야 하는가?

### 빼먹기 쉬운 결정 점검

- 각 법령·표준에 대해 *우리가 어떻게 준수하는지*의 한 줄 명시?
- 인증·심사가 *우리에게* 필요한 것 vs *결과물에* 필요한 것이 분리되었는가?
- 법령 *충돌*이 있을 때(예: 데이터 보존 의무 vs 삭제 요구권)의 해석 입장이 명시되었는가?

---

## 5. Technical Approach

**목적**: *어떻게* 만들 것인가. 아키텍처, 기술 선택, 개발 방법론, 품질 관리.

### 결정에 필요한 입력

- 시스템 *고수준 아키텍처*?
- *기술 스택* 선택과 그 정당화? (특히 RFP가 *국산 SW 우선* 같은 제약을 둔 경우)
- *개발 방법론*? (waterfall / agile / hybrid — 공공은 waterfall 친화)
- *품질 관리 체계*? (테스트 단계, 품질 지표, 결함 관리)
- *형상 관리·산출물 관리* 방안?

### 빼먹기 쉬운 결정 점검

- 각 기술 선택이 *RFP 요구* 또는 *법령*과 정합하는가? (예: 클라우드 사용 가능 여부)
- *오픈소스 사용*에 대한 라이선스·보안 정책이 명시되었는가?
- *기존 시스템 연동*의 인터페이스 명세가 RFP 명시 표준에 부합하는가?
- *데이터 마이그레이션*의 절차·검증 방법이 명시되었는가?
- *성능 검증* 방법이 RFP 비기능 요구의 검증 가능 형태로 정의되었는가?

---

## 6. Management Approach & Key Personnel

**목적**: 사업 *수행 체계*와 *핵심 인력*. 공공 평가에서 인력 점수는 큰 비중.

### 결정에 필요한 입력

- 사업 PM은 누구이며 그의 *경력·자격·역할*?
- 핵심 인력(아키텍트, 보안 책임자, 품질 책임자 등) 각각의 자격·경력·투입률?
- *조직 구조도* — 의사결정·보고 라인?
- *발주처와의 커뮤니케이션 체계* — 정례 회의, 보고 주기, 문서화 방식?
- *위험·이슈 관리 체계*?

### 빼먹기 쉬운 결정 점검

- 각 인력의 *자격증·학위*가 RFP 요구 자격을 *증빙 가능한 형태*로 매핑되었는가?
- 인력의 *투입 기간*이 일정에 정합하는가?
- 인력 *교체 시 절차*가 명시되었는가? (공공은 교체 빈도 제한이 흔함)
- *예비 인력*(백업)이 정의되었는가?
- 우리 측 *대표 1인* 권한 범위가 명확한가?

---

## 7. Past Performance

**목적**: *유사 사업 수행 경험*의 증거. 공공 평가에서 가산점의 핵심.

### 결정에 필요한 입력

- 본 사업과 *유사한* 과거 수행 실적은? (3–5건)
- 각 실적의 *발주처 / 사업명 / 사업비 / 수행 기간 / 우리 역할*?
- 각 실적이 *현재 사업과 어떻게 유사한지* 1줄 매핑?
- *수행 결과*의 정량 지표가 있다면? (사용자 수 / 가용성 / 만족도)

### 빼먹기 쉬운 결정 점검

- 각 실적의 *증빙 자료*(계약서 / 완료 확인서 / 발주처 추천서)가 확보되었는가?
- *우리가 직접 수행*한 부분과 *컨소시엄/하청*으로 수행한 부분이 구분되었는가?
- 실적이 *최근*인가, *오래된 실적의 비중*이 너무 크지 않은가?
- *공공 사업 실적*과 *민간 사업 실적*의 균형이 RFP 평가 기준에 맞는가?

### 형식 (illustrative)

| 사업명 | 발주처 | 사업비 | 기간 | 우리 역할 | 본 사업과의 유사성 |
|---|---|---|---|---|---|
| {project} | {agency} | {amount} | {YYYY-MM ~ YYYY-MM} | {role} | {1-line mapping} |

## 8. Deliverables Schedule

**목적**: 산출물 인도 일정. 공공 사업의 *단계 검수*와 정렬.

### 결정에 필요한 입력

- 사업 *단계 구분*은? (착수 / 분석 / 설계 / 구현 / 시험 / 이행 / 안정화)
- 각 단계의 *산출물*과 *검수 시점*?
- 사업 *총 기간*과 *마일스톤*?
- *검수 절차*는? (자체 검수 / 발주처 검수 / 감리 검수의 순서·기간)

### 빼먹기 쉬운 결정 점검

- 각 산출물이 *RFP 요구 산출물 목록*과 1:1 매핑되는가?
- *감리 일정*이 별도 반영되었는가? (공공은 감리가 흔히 강제)
- *발주처 휴무·결재 일정*이 반영되었는가?
- 단계별 *지연 리스크*에 대한 buffer 또는 대응책이 명시되었는가?

---

## 9. Audit & Reporting Response

**목적**: 사업 수행 중·후의 *감사·보고* 응답 체계. 공공 사업 종료 후 수년간 지속될 수 있는 *감사 대응 의무*.

### 결정에 필요한 입력

- 사업 중 *정기 보고*의 주기·형식·수신자?
- *감리 대응* 체계는? (감리 지적 → 우리 측 대응 → 재검토 사이클)
- 사업 *종료 후 감사*에 응할 *문서·로그 보존* 방안과 기간?
- *외부 감사* 또는 *국정감사* 요청 시 응답 절차?

### 빼먹기 쉬운 결정 점검

- 보고 *형식*이 발주처 표준 양식인가, 우리 양식인가?
- 감리 지적 *불복 시 절차*가 명시되었는가?
- 사업 종료 후 *문서 보존 기간*이 법정 기간 이상인가?
- 사업 종료 후 *연락 가능한 책임자*가 지정되었는가? (퇴사·부서 이동에도 유효한 형태로)

---

## 10. Resolved Assumptions

**목적**: 발주처와 *합의* 또는 *명시적 가정*으로 간주되는 사항. 미해결 가정은 여기 들어오지 않는다 (Initiative로 또는 발주처 사전 질의로).

### 결정에 필요한 입력

- 발주처가 *제공*하기로 한 것? (계정 / 시설 / 데이터 / 시간)
- *발주처 측 조건*에 대한 우리의 가정은? (예: 기존 시스템 가용성, 데이터 품질)
- *외부 환경*에 대한 가정? (관련 법 개정 부재 / 정책 변동 부재)

### 빼먹기 쉬운 결정 점검

- 각 가정에 *발주처 측 검증자 / 시한*이 명시되었는가?
- 가정이 *깨질 경우*의 절차가 명시되었는가?
- 발주처 *미제공* 시 책임 분담은?
- *RFP 본문에 명시된 가정*과 *우리가 추가로 두는 가정*이 분리되어 있는가?

---

## 11. Executive Summary

**목적**: 평가위원이 *제일 먼저 1페이지로* 읽는 응답의 요약. 본 섹션은 *마지막*에 작성한다.

### 결정에 필요한 입력

- 우리가 이 사업에 *적합한* 핵심 1–3줄?
- 기술 접근의 *차별점* 1–3줄?
- 인력·실적의 *강점* 1–2줄?
- 컴플라이언스·법령 준수 *완전성* 1줄?
- 사업비·일정 *준수 의지* 1줄?

### 빼먹기 쉬운 결정 점검

- 본문 모든 섹션의 *결론*이 Executive Summary에 빠짐없이 반영되었는가?
- *RFP의 평가 기준 가중치*에 부합하는 우선순위로 강조되었는가?
- *과장된 주장*(증빙 없는 1위/최고)이 없는가? — 공공 평가는 과장 표현에 감점.
- 길이가 *1–2 페이지*에 들어가는가?
