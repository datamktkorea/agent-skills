# Product Branch Template — Project Steering

**분기**: `product` (자사 SaaS / 내부 제품)
**산출물 명칭**: *Project Steering*
**산출 위치**: Project DB 해당 프로젝트 페이지 본문

> **이 템플릿이 다루는 것**
>
> 시간에 의존하지 않는 invariants — 비전, 비즈니스 규칙, 도메인 언어, 멀티테넌시, i18n, 권한, 컴플라이언스. 코딩 에이전트가 매 세션 시작 시 fetch하는 SSOT.
>
> **이 템플릿이 다루지 않는 것**
>
> 성공 지표, 마일스톤, 일정, 활성 위험, 미결정 — 모두 Initiative 레이어로.
>
> **이 템플릿의 예시**
>
> 본 템플릿의 모든 도메인 예시(SaaS, 결제, 의료, 학생, 환자, 기관 등)는 *형태를 보여주기 위한 illustrative*다. 실제 작성 시 자기 도메인의 값으로 대체한다. 예시 문자열을 룩업 테이블처럼 가져다 쓰지 않는다.

## 권장 작성 순서

의존성을 따라가는 순서. SKILL.md Phase 0.5에서 announce할 때 그대로 사용한다.

1. **Vision / Mission**
2. **Non-goals / Out of Scope**
3. **Design Principles**
4. **Target Market & Users**
5. **Domain Glossary** ← 이후 모든 섹션이 사용
6. **Business Rules** (도메인 불변식)
7. **Permissions & Role Model**
8. **Monetization Rules & Access Tiers** ← Permissions 다음
9. **Multi-tenancy & Data Isolation**
10. **i18n / l10n Invariants**
11. **Audit / Logging / Compliance**
12. **External Interfaces & Dependencies**
13. **Resolved Architectural Assumptions**

근거: Vision/Non-goals/Principles가 frame을 설정 → Target이 다운스트림 결정에 영향 → Glossary가 Business Rules의 어휘 제공 → Permissions가 Monetization tier에 선행 → Multi-tenancy/i18n/Audit는 독립 architectural invariants → External Interfaces는 제품 표면이 결정된 후 → Resolved Assumptions는 catch-all.

## 1. Vision / Mission

**목적**: 이 제품이 *누구의 어떤 세상*을 만들려는지 한 단락(2–3문장)으로 명문화. 2–5년 horizon. 변경 빈도 < 연 1회.

### 결정에 필요한 입력

- 누구의 삶/일이 이 제품으로 어떻게 달라지는가? (사용자 관점)
- 이 제품이 없을 때 사람들이 *불완전하게* 하고 있는 일은 무엇인가?
- 5년 후 이 제품이 존재하는 시장에서 *없어지는 행동*은 무엇인가?

### 빼먹기 쉬운 결정 점검

- 비전이 *측정 가능*하지 않아도 *판단 가능*한가? (어떤 기능 제안이 비전에 부합/반함을 누군가가 답할 수 있는가)
- 비전이 회사 미션/모회사 전략과 충돌하지 않는가?
- 사용자가 아닌 *경쟁사 시점*에서 정의되어 있지 않은가? ("X보다 빠른" 류는 비전이 아니라 포지셔닝)

---

## 2. Non-goals / Out of Scope

**목적**: 이 제품이 *의도적으로* 하지 않는 것의 명시. AI 에이전트가 인접 영역으로 over-engineering하는 것을 막는 1차 방어선. Shape Up "No-Gos" / GitHub Spec Kit 메인스트림 패턴.

### 결정에 필요한 입력

- 사용자가 자주 요청하지만 *의도적으로* 하지 않을 것은? (이유 1줄 동반)
- 인접 시장/경쟁사가 하지만 *우리는* 하지 않을 것은?
- "다음 버전에서"가 아닌 *영구적으로 안 함*은?

### 빼먹기 쉬운 결정 점검

- 각 Non-goal에 *왜 안 하는지* 1줄 근거가 붙어 있는가? (없으면 Vision 드리프트와 구별 안 됨)
- "지금은 안 함"인 항목이 섞이지 않았는가? 그것은 Initiative scope이지 Non-goal이 아니다.
- Non-goal이 Vision과 명시적으로 충돌하지 않는가?

---

## 3. Design Principles

**목적**: 모든 설계·코드 결정이 갈등할 때 어느 쪽으로 기울어야 하는지 정한 3–7줄의 휴리스틱. 한 줄 = 한 원칙. 7개 초과 시 약화된다.

### 결정에 필요한 입력

- 두 좋은 옵션이 충돌할 때 *기본적으로* 어느 쪽인가? (예: 단순함 vs 기능 풍부함, 즉시 vs 일관성, 자동 vs 명시)
- 사용자 경험에서 *절대 깎지 않는* 한 가지는?
- 엔지니어링에서 *절대 받아들이지 않는* 한 가지는?

### 빼먹기 쉬운 결정 점검

- 각 원칙이 *반대 표현 가능*한가? ("좋은 UX를 추구한다"는 원칙이 아니다 — 누구나 동의할 수 있기 때문. "버튼이 늘기보다 줄게 한다"는 원칙이다.)
- 7개를 넘지 않는가? (8개 이상은 사실상 우선순위 없는 위시리스트)
- 원칙끼리 *충돌* 시 어느 쪽이 이기는지 명시되어 있는가?

---

## 4. Target Market & Users

**목적**: 누구를 위한 제품인지 정의. 페르소나가 아닌 *행위자(actor)* 관점. AI 에이전트가 "이 변경이 누구에게 영향을 주는가"를 판단하는 기준.

### 결정에 필요한 입력

- 1차 사용자(daily user)는 누구인가? 역할명/직무/맥락 1줄.
- 1차 구매자(buyer)는 누구인가? 사용자와 동일한가, 다른가?
- 명시적 비대상(out-of-persona)은? — "이 제품은 X에게 맞지 않다"

### 빼먹기 쉬운 결정 점검

- *집단의 어디까지가 우리의 사용자인가*가 명시되었는가? (예: "병원의 의사" — 봉직의만? 개원의? 양쪽? 간호사는 대상인가 아닌가?)
- 구매자 vs 사용자가 다를 때, 둘 사이의 권한 관계가 명시되었는가? (Permissions 섹션의 입력이 됨)
- 비대상 사용자에게 *우연히 노출되는* 것을 어떻게 막는가?

---

## 5. Domain Glossary

**목적**: 도메인 고유 용어의 ubiquitous language 정의. *코드, 화면, 문서, 회의록*에서 동일한 단어가 동일한 뜻이 되도록.

### 결정에 필요한 입력

- 도메인에 *의미가 충돌하는 단어*가 있는가? (예: "주문" — 카트의 주문인가, 결제 후 주문인가, 출고된 주문인가)
- 외부 표준어/업계 용어와 *내부 명명*이 다를 때, 어느 쪽을 코드에 쓰는가?
- 한국어/영어 매핑이 필요한 용어는?

### 빼먹기 쉬운 결정 점검

- 각 용어 정의가 *반례*를 포함하는가? (예: "병원: 의료법 3조의 의료기관 중 30병상 이상. **30병상 미만은 의원이지 병원이 아님**")
- 동음이의어를 *명시적으로* 분리했는가? ("요청"이 Request DB의 Request인지 HTTP request인지)
- 코드에 영어 식별자로 들어갈 표기가 정해졌는가? (camelCase / snake_case 1차 결정은 Repo Steering이지만 *어휘* 매핑은 여기)

### 형식 (illustrative)

| 한국어 | 영어 식별자 | 정의 | 반례/주의 |
|---|---|---|---|
| {term-ko} | {term_en} | {one-line definition} | {what it is NOT} |

## 6. Business Rules (도메인 불변식)

**목적**: *어떤 상태가 반드시 참인가*. 코드의 모든 분기·검증·계산이 의존하는 도메인 진리. *기능*이 아닌 *불변식*.

### 결정에 필요한 입력

- "X는 절대 ~ 일 수 없다" 형식의 진술은? (예: "주문은 결제 없이 출고될 수 없다", "환불은 결제 금액을 초과할 수 없다")
- 도메인 객체 간 *count/cardinality* 제약은? (예: "한 사용자는 한 조직에만 속한다" vs "여러 조직 동시 가입 가능")
- 시간/순서 제약은? (예: "취소는 결제 후 7일 이내에만 가능 — 단, 7일은 비즈니스 규칙이고 Steering에 들어감. '오늘 기준 7일 후가 며칠'은 Initiative")

### 빼먹기 쉬운 결정 점검

- 각 규칙이 *코드의 어디에선가 검증 가능*한가? (DB 제약 / 도메인 메서드 / API 게이트)
- 규칙끼리 *충돌*하는 쌍이 없는가?
- 규칙 위반 시 *기본 동작*이 정의되었는가? (reject / log / soft-fail)
- *예외*가 있는 규칙은 그 예외 조건이 명시되었는가?

### 형식 (illustrative)

`BR-001: 주문 단위는 결제 단위와 1:1이다 (한 주문은 한 결제, 한 결제는 한 주문). — 위반 시 reject`

## 7. Permissions & Role Model

**목적**: 역할(role)과 그 역할이 가진 권한의 정의. 모든 authorization 분기의 SSOT.

### 결정에 필요한 입력

- 시스템에 존재하는 역할 목록은? (사용자 관점 — admin, member 같은 시스템 역할이 아니라 도메인 역할 — 예: 의사, 간호사, 원무팀, 환자)
- 역할 간 *위계*가 있는가? (상위 역할은 하위의 모든 권한을 갖는가, 아니면 직교(orthogonal)인가)
- *조건부 권한*이 있는가? (예: 본인 환자만 / 본인 조직만 / 시간대 제한)

### 빼먹기 쉬운 결정 점검

- 역할 목록과 Section 4 Target Users의 행위자가 1:1로 매핑되는가?
- 권한 부여/회수 *주체*가 정의되었는가? (누가 누구에게 역할을 줄 수 있는가)
- *비활성 사용자*(suspended/expired)는 어느 권한을 잃고 어느 권한을 유지하는가?
- 시스템 레벨 역할(super-admin, support)이 도메인 역할과 분리되었는가?

### 형식 (illustrative)

| 역할 | 핵심 권한 | 조건부 권한 | 부여 주체 |
|---|---|---|---|
| {role} | {capabilities} | {if-conditions} | {who can grant} |

## 8. Monetization Rules & Access Tiers

**목적**: *코드에 영향을 주는* 가격 게이팅 규칙. 가격 *전략*(price points, 할인 정책, 프로모션)은 여기 들어오지 않는다 — 그것은 Initiative/세일즈 문서.

### 결정에 필요한 입력

- 어떤 access tier가 존재하는가? (예: free / pro / enterprise — 그러나 *티어 이름 자체가 Steering 결정*)
- 각 tier가 *접근 불가*한 capability는? (티어 게이팅의 enforcement 지점)
- tier 변경 시 *코드 동작*은? (즉시 / 다음 결제일 / 그레이스 기간)

### 빼먹기 쉬운 결정 점검

- "free 사용자는 X 기능 못 씀"이 *어디에서* enforce되는가? (UI 숨김만? API 거부? DB 레벨?)
- *다운그레이드* 시 기존 데이터는 어떻게 되는가? (read-only / 일정 기간 후 삭제 / 영구 보존)
- *결제 실패* 상태의 사용자는 어느 권한을 잃는가?
- tier가 *역할(Section 7)*과 *직교*인가, *교차*하는가?

---

## 9. Multi-tenancy & Data Isolation

**목적**: 테넌트 경계의 정의. *어디까지가 격리 단위*이며 그 격리가 *어떻게 enforce*되는가.

### 결정에 필요한 입력

- tenant 단위는? (조직 / 워크스페이스 / 개인 / 없음 — single-tenant)
- 격리 모델은? (DB 분리 / schema 분리 / row-level / 없음)
- *cross-tenant 작업*이 정당한 경우는? (admin 통계, 지원 업무, 백업 — 각각의 정당화)

### 빼먹기 쉬운 결정 점검

- 모든 도메인 객체가 *tenant 키*를 명시적으로 갖는가?
- *cache / queue / log*의 격리는?
- 테넌트 *생성/삭제*의 lifecycle은? (soft-delete 보존 기간, 데이터 export 권리)
- *테넌트 간 데이터 이동*이 정당한 시나리오와 그 경로가 명시되었는가?

---

## 10. i18n / l10n Invariants

**목적**: *시간 불변* 결정만 — "이 제품은 다로케일을 지원하는가, 어느 layer에서 지원하는가". 지원 로케일 *목록*과 번역 *상태*는 Initiative 레이어.

### 결정에 필요한 입력

- 시스템 메시지(에러, 알림, 메뉴) 다로케일 — yes/no?
- 사용자 콘텐츠(사용자가 입력하는 데이터) 다로케일 — yes/no? (예: 글의 다국어 제목)
- 관리자 영역 다로케일 — yes/no?
- *날짜/시간/통화/숫자 포맷*의 로케일 의존 — 어디서 결정되는가? (사용자 / 테넌트 / 콘텐츠)

### 빼먹기 쉬운 결정 점검

- "지금은 한국어만"인 항목이 있다면 그것은 Initiative scope이지 Steering 결정이 아니다 — 정말 *영구적으로 단일 로케일*인지 확인.
- 다로케일이라면 *모든 사용자 텍스트가 외부화(externalized)*된다는 invariant가 명시되었는가?
- *RTL 언어 지원*은 별도 invariant인가, 미지원인가?
- 시간대(timezone) 처리: 사용자 / 테넌트 / 서버 — 무엇을 기준으로 저장·표시하는가?

---

## 11. Audit / Logging / Compliance

**목적**: 규제·감사·포렌식이 요구하는 *영구* 제약. 무엇을, 얼마나 오래, 어떤 형태로 기록해야 하는가.

### 결정에 필요한 입력

- 적용되는 규제는? (GDPR / 개인정보보호법 / 의료법 / 전자금융감독규정 / SOC2 / ISO27001 — 해당하는 것)
- 각 규제가 요구하는 *데이터 보존 기간*은? (예: 결제 기록 5년)
- 각 규제가 요구하는 *감사 로그* 항목은? (누가 / 언제 / 무엇을 / 어떻게 — 의 어느 조합)
- *PII* 정의: 우리 도메인에서 PII는 정확히 무엇인가?

### 빼먹기 쉬운 결정 점검

- 감사 로그 *수정 불가성*(append-only, immutable)이 보장되는가?
- *시간 동기화*(NTP)가 감사 신뢰성에 충분한가?
- *백업*의 보존/암호화/접근통제는?
- 데이터 *삭제 요구권*(right to erasure)와 보존 의무가 충돌할 때의 해결 절차는?
- 사용자 *export 권리*(data portability)의 형식과 범위는?

---

## 12. External Interfaces & Dependencies

**목적**: 외부 시스템과의 *안정적 약속*. 어느 외부 의존이 *영구적*이며 그 인터페이스가 *어디에 명세*되어 있는가.

### 결정에 필요한 입력

- 결제, 인증, 메시징, 분석 등 *영구 외부 의존*은? (1년 내 교체 가능성이 낮은 것)
- 각 의존의 *공식 명세 위치*는? (URL / 사내 위키)
- 외부 장애 시 *기본 동작*은? (fail-fast / fail-soft / queue & retry / fallback)

### 빼먹기 쉬운 결정 점검

- 각 의존이 *교체 가능*한 추상 뒤에 있는가, 아니면 *직접 결합*인가? (직접 결합이라면 그 정당화)
- *데이터 거주성*(외부 SaaS의 서버 위치)이 컴플라이언스(Section 11)와 충돌하지 않는가?
- 외부 시스템의 *인증·인가 방식*(OAuth / API Key / mTLS)과 그 비밀 관리 위치?
- *SLA 가정* — 외부가 제공하는 SLA가 우리 SLA에 어떻게 반영되는가?

---

## 13. Resolved Architectural Assumptions

**목적**: 명시적으로 *결정되어 invariant가 된* 아키텍처 가정의 카탈로그. 다른 섹션에 흡수되지 않는 횡단 가정을 모은다. *미해결* 가정은 여기 들어오지 않는다 (Initiative로).

### 결정에 필요한 입력

- 인증 방식: SSO-only / 로컬 인증 허용 / 둘 다 — 어느 쪽?
- 클라이언트 종류: 웹만 / 모바일 포함 / 데스크톱 — 어느 범위?
- 단일 region / 멀티 region?
- 동기 처리 / 비동기 처리의 기본 — 어느 쪽?
- 그 외, "이건 변하지 않을 것"으로 합의된 cross-cutting 결정 일체.

### 빼먹기 쉬운 결정 점검

- 각 항목이 *왜 invariant인지* 1줄 근거가 붙어 있는가? (없으면 Initiative scope과 구별 안 됨)
- 다른 섹션에 흡수 가능한 항목이 잘못 여기 와있지 않은가? (예: 인증 방식은 Permissions 또는 External Interfaces에 흡수 가능)
- *변경 시 영향 범위*가 명시되었는가? (이 invariant가 깨지면 어느 섹션이 같이 흔들리는지)
