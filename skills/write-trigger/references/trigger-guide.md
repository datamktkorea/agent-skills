# 트리거 문서 작성 가이드

트리거 문서는 개발을 시작하기 전에 "왜 이 일을 하는가"를 팀이 공통된 언어로 정의하는 문서다.
이 가이드는 Claude 없이 혼자 작성할 때도 참고할 수 있도록 만들어졌다.

---

## 트리거 문서 구조

```
트리거 유형:   Fix | Build | Improve | Strategy
우선순위:      P0 | P1 | P2 | P3
발신자:        고객 | 내부 팀 | 경영진 | 모니터링 시스템
작성일 / 작성자:

## Problem Statement
[누가] [어떤 상황에서] [무엇이] 안 된다

## 배경 및 맥락
(이 문제가 발생한 경위, 언제부터, 어떤 조건에서)

## 기대 결과
이 문제가 해결되면 어떤 상태여야 하는가

## 참고 자료
(스크린샷, 로그, 관련 이슈 링크 등 — 선택)
```

---

## 트리거 유형 4가지

### 🔴 Fix — 원래 돼야 하는데 안 됨

기존에 동작하거나 동작해야 한다고 설계된 기능이 깨진 경우.
버그, AI 출력 오류, 장애, 데이터 정합성 문제가 여기에 해당한다.

**판단 기준:** "이전에는 됐는가?" 또는 "설계상 돼야 하는가?" → YES면 Fix

**발신자:** 고객 리포트, 모니터링 알림, 내부 QA 발견 모두 가능

---

### 🟡 Build — 사용자가 필요한데 존재하지 않음

현재 시스템에 없는 기능이나 흐름을 새로 만드는 경우.
사용자가 목표를 달성하기 위해 우회하거나 포기하고 있다면 Build 트리거다.

**판단 기준:** "기능 자체가 없어서 못 하는가?" → YES면 Build

**발신자:** 고객 요청, 영업/CS 경유, 사용성 리서치 결과

---

### 🔵 Improve — 되긴 하는데 충분하지 않음

기능은 존재하지만 속도, 정확도, UX, 유지보수성 등이 기대 수준에 못 미치는 경우.
"되긴 해"라는 말이 나온다면 Improve를 먼저 검토하라.

**판단 기준:** "기능은 있는데 불만족스러운가?" → YES면 Improve

**발신자:** 사용자 피드백, 내부 개발팀, 성능 지표 이상

---

### 🟢 Strategy — 비즈니스 또는 시장 방향 변화

사용자 문제가 아니라 계약 조건, 규제 대응, 경쟁사 대응, 사업 방향 전환 등 외부 요인에 의해 시작되는 경우.

**판단 기준:** "사용자 불편이 아니라 비즈니스 이유가 있는가?" → YES면 Strategy

**발신자:** 경영진, 법무/컴플라이언스, 사업 개발

---

## 우선순위 기준 (P0–P3)

| 등급 | 기준 | 대응 기준 |
|------|------|-----------|
| **P0** | 사용자가 핵심 작업을 완료할 수 없음 / 매출에 즉각 영향 | 즉시 대응 |
| **P1** | 주요 기능 손상, 우회 방법 없거나 매우 어려움 | 이번 주 내 |
| **P2** | 불편함 있지만 우회 방법 존재 | 이번 스프린트 |
| **P3** | 개선하면 좋지만 지금 당장은 아님 | 백로그 |

**P0와 P1을 구분하는 핵심 질문:** "지금 이 순간 사용자가 서비스를 전혀 못 쓰는가?"
→ YES면 P0, 힘들지만 뭔가 할 수 있으면 P1

---

## Problem Statement 작성 기준

### 형식 (반드시 준수)

```
[누가] [어떤 상황에서] [무엇이] 안 된다
```

세 요소 모두 있어야 작성 완료다. 하나라도 빠지면 다시 작성한다.

### 측정 가능한 표현 원칙

다음 표현은 사용 금지다:

| 금지 표현 | 이유 |
|-----------|------|
| 가끔, 종종, 자주 | 빈도 불명확 |
| 느리다, 오래 걸린다 | 기준값 없음 |
| 이상하다, 이상한 결과 | 증상 불명확 |
| 사용자들이 불편해한다 | 누가, 어떤 상황 불명확 |

대신 시점, 조건, 횟수, 수치로 표현한다.

## 나쁜 예 / 좋은 예

### 예시 1 — Fix

**나쁜 예:**
> AI가 가끔 이상한 목차를 생성한다

문제: "가끔"은 측정 불가. "이상한"은 어떻게 이상한지 알 수 없음. 누가 겪는지 불명확.

**좋은 예:**
> 현장 실무자가 100페이지 이상의 PDF를 업로드한 직후 목차 생성 버튼을 누르면, AI가 챕터 제목을 빈 문자열로 반환한다

---

### 예시 2 — Build

**나쁜 예:**
> 사용자들이 진행 상황을 알고 싶어한다

문제: 누가, 언제, 어떤 상황인지 없음. 해결 방향도 열려있지 않고 너무 넓음.

**좋은 예:**
> 현장 실무자가 소스를 업로드한 뒤 목차 생성 완료 여부를 확인하려고 화면을 반복 새로고침한다

---

### 예시 3 — Improve

**나쁜 예:**
> 내부 코드가 복잡해서 유지보수가 어렵다

문제: 어떤 코드인지, 어떤 상황에서 어떤 문제가 생기는지 특정되지 않음.

**좋은 예:**
> 백엔드 개발자가 AI 모델을 교체할 때 파이프라인 파일 3곳을 수동으로 수정해야 하며, 한 곳이라도 누락되면 에러 없이 이전 모델이 호출된다

---

### 예시 4 — Strategy

**나쁜 예:**
> 경쟁사가 다국어 기능을 출시했으니 우리도 해야 한다

문제: 비즈니스 맥락이 없고, 언제까지 왜 해야 하는지 불분명.

**좋은 예:**
> 기업 고객사 A사가 계약 갱신 조건으로 영어·일본어 인터페이스 지원을 2026년 6월 1일까지 요구했으며, 미이행 시 계약이 종료된다

---

## 자주 하는 실수

**"고객 피드백이 왔으니 고객 피드백 트리거"** — 틀렸다.
발신자는 유형 분류에 영향을 주지 않는다. 고객이 말했더라도 실제 성격이 Fix라면 Fix다.

**두 유형이 겹치는 것 같을 때** — 더 근본적인 문제를 선택한다.
AI 품질이 나쁘다는 고객 불만 → Fix (품질 저하)인지, Build (피드백 수집 기능 없음)인지 근본 원인으로 판단.

**P0 남발** — P0는 "지금 이 순간 서비스가 멈췄다"는 뜻이다.
불편함이 크더라도 우회 방법이 있으면 P1이다.
